# v1.2.0 배포 검수 기록

2026-11-20에 범용 v1.1.0과 v1.2.0, 전문 스킬 v1.0.0과 v1.1.0을 비교했다. 아래 설계 평가는 빈 프로젝트에서 GPT-6 Sol이 작성한 답변을 대상으로 했다. 각 행의 이전판과 후보판은 같은 요청을 별도 대화에서 받았다. 엔진·앱 실행 결과와 구분해, 예측한 관찰값과 이를 확인할 방법이 답변에 있는지 판정했다.

| 사례 | 기존판에서 확인한 설계 | 후보판에서 확인한 설계 | 판정 |
| --- | --- | --- | --- |
| Unity U1 | 세션이 점수를 보존하고 HUD가 활성·비활성 시 구독을 연결·해제한다. 복귀 10점, 다음 득점 15점, 새 판 0점이다. | 같은 결과에 복귀 후 현재 HUD의 득점 알림 1회, 이전 HUD 0회를 명시했다. | 통과 → 통과 |
| Godot G1 | 구매 후 7G·1기, 새 런 10G·0기, 인스턴스별 상태를 설명했다. 상점 단독 검증에 넘길 런 상태가 모호했다. | 버튼에서 런까지 구매 호출을 추적하고 상점을 세 번 다시 열어도 7G·1기인 경우와 테스트용 런 주입을 제시했다. | 부분 충족 → 통과 |
| Unreal E1 | 서버가 중복 요청을 거절하고 PlayerState 점수를 복제한다. 부활·중간 참가 뒤 점수 1과 과거 연출 미재생을 확인한다. | 서버와 A·B·C 관찰표에서 같은 점수와 연출 횟수를 확인한다. | 통과 → 통과 |
| Flutter F1 | 화면 이탈 후 저장 지속과 중복 방지는 다뤘다. 첫 요청의 실패를 재시도 성공 뒤에 전달하는 시험은 빠졌다. | 응답 순서를 제어해 재시도가 성공한 뒤 첫 실패가 도착해도 목록 1행과 성공 상태가 유지되는지 확인한다. | 부분 충족 → 통과 |
| Rust R1 | 한 트랜잭션과 ID 고유 제약을 선택했다. 저장 실패의 종료 상태는 ‘0이 아닌 값’으로 적었다. | 공개 CLI에서 실패·복구·재실행 후 행 수 0→2→2, 종료 상태 1→0→0, X의 거절 이유를 확인한다. | 부분 충족 → 통과 |
| Flutter + Rust M1 | 같은 요청 ID로 기존 예약을 되찾고 다른 사용자는 충돌, DB에는 한 건이 남는다. 사본 버전은 기록되지 않았다. | 범용 스킬만 있는 홈에서 두 전문 ZIP을 실제로 설치했다. 답변은 양쪽 사본을 각각 v1.1.0 배포 파일 일치로 보고하고 두 화면과 예약 한 건을 같은 표로 연결했다. | 예약 규칙 유지, 버전 보고 추가 |

<summary>설계 평가에 사용한 요청</summary>

- **U1** Unity 게임에서 한 판에 10점을 얻고 결과 씬에 갔다가 같은 판으로 돌아와 5점을 더 얻습니다. HUD는 점수를 얻을 때마다 알리고, 새 게임을 누르면 새 판을 시작합니다. 이 흐름의 구조와 검증 방법을 설계해 주세요.
- **G1** Godot의 깍두기 공방에서 10G로 시작해 3G짜리 타워 하나를 산 뒤 웨이브를 진행합니다. 같은 런에서 상점을 여러 번 다시 열기도 하고 새 런도 시작합니다. 두 타워는 같은 정의를 쓰고 런타임 상태는 개별입니다. 구조와 검증 방법을 설계해 주세요.
- **E1** Unreal 협동 게임에서 A가 유물을 획득하면 1점을 줍니다. A의 획득 요청이 중복될 수 있고 부활 후에도 점수는 남습니다. B는 처음부터 있고 C는 득점 연출이 끝난 뒤 들어옵니다. 구조와 테스트에서 누가 무엇을 확인할지 설계해 주세요.
- **F1** Flutter 습관 기록 앱에서 사용자가 습관 하나를 저장하고 즉시 이전 목록으로 돌아갑니다. 저장은 화면을 떠나도 계속돼야 합니다. 타임아웃 뒤 재시도할 수 있고, 이전 시도의 응답이 늦게 올 수 있습니다. 구조와 검증을 설계해 주세요.
- **R1** Rust CLI가 ID가 있는 CSV 행 A, B와 형식 오류 행 X를 읽어 정상 행을 한 묶음으로 SQLite에 저장하고 거절 이유를 요약합니다. B를 쓰는 중 저장 장치가 실패할 수 있고 사용자가 같은 파일을 다시 실행합니다. 중복 ID는 한 번만 저장합니다. 셸에서는 저장 장애만 실패로 처리합니다. 구조와 검증을 설계해 주세요.
- **M1** Flutter 앱과 Rust API에서 두 사용자가 같은 예약 슬롯을 신청할 수 있습니다. 성공한 사용자는 응답을 받기 전에 화면을 닫았다가 같은 동작을 다시 시도합니다. 두 사람의 화면과 DB에서 어떤 일이 일어나는지 구조와 검증 방법을 설계해 주세요.

## 실제로 실행한 검수

| 대상 | 실행과 결과 |
| --- | --- |
| 설치·조회 CLI | Windows와 Ubuntu(WSL)에서 표준 라이브러리 단위 테스트를 실행했다. 원래의 한 줄 경로 출력, JSON 조회, 설치 기록 쓰기 실패, 동시 설치, 같은 이름의 두 사본, 수정·누락·추가 파일, 같은 바이트를 가진 두 태그를 포함한다. |
| 공식 ZIP과 읽기 전용 경로 | 각 OS에서 전문 단독 ZIP 10개와 Unity 합본 두 버전을 공백이 있는 임시 경로에서 검사했다. 구판 5종은 설치 기록과 VERSION 없이 v1.0.0으로, 신판 5종은 v1.1.0으로 확인됐다. 쓰기 시도가 거부된 디렉터리에서 조회를 반복하고, 수동 설치한 Unity 참고 문서를 고치면 조회가 미확인으로 바뀌고 수정본은 보존되는지 확인했다. |
| 버전 근거의 강도 | 전문 스킬 단독 호출에서는 동봉 VERSION을 선언 버전으로 보고했다. Python을 쓸 수 없는 조건에서는 PowerShell로 Godot ZIP과 개별 파일의 SHA-256을 실제로 대조해 v1.1.0을 식별했다. |
| 인덱스 재생성 | Windows와 Linux에서 공식 ZIP과 두 카탈로그로 생성한 인덱스의 SHA-256은 `e7129df48f16544cf9d5c4e4ce721712dbbe16ade23fc9e4f10ec18704e21bb6`이었다. 기존 Unity v1.0.0 단독 ZIP의 DOS 경로 구분자도 처리한다. |

## 재현

범용 저장소 루트에서 `python3 -m unittest discover -s tests -v`를 실행한다. 실제 릴리스 검수에는 아래 두 디렉터리에 ZIP을 원래 자산 이름으로 둔다.

| 디렉터리 | 단독 전문 ZIP 5개 | 범용 ZIP |
| --- | --- | --- |
| `baseline/` | 각 전문 저장소의 v1.0.0 | 범용 v1.1.0의 기본 ZIP과 Unity 합본 |
| `current/` | 각 전문 저장소의 v1.1.0 | 범용 v1.2.0의 기본 ZIP과 Unity 합본 |

```sh
python3 tests/check_release_archives.py --baseline baseline --current current
```

쓰기 제한을 우회하지 않는 일반 계정에서 실행한다. 구판 ZIP을 Linux에서 수동으로 풀 때는 DOS 경로 구분자를 지원하는 압축 도구를 사용한다. 인덱스를 처음부터 재생성하려면 구판과 신판의 카탈로그를 차례로 같은 새 출력 파일에 적용한다.

```sh
git show v1.1.0:references/specialists.json > baseline/catalog.json
python3 scripts/build_release_index.py --catalog baseline/catalog.json --archives baseline --index rebuilt.json
python3 scripts/build_release_index.py --catalog references/specialists.json --archives current --index rebuilt.json
git diff --no-index references/release-index.json rebuilt.json
```
