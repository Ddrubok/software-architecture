# 전문 스킬을 고르고 현재 설계에 적용하기

사용자가 지정한 기술과 이번에 정해야 하는 구조를 함께 본다. 기존 프로젝트라면 요청과 관계있는 실행 경로와 설정을 확인한다. 예를 들어 `pubspec.yaml`의 Flutter SDK 의존성은 Flutter 앱의 근거가 된다. 저장소에 예제나 빌드 도구로 등장하는 언어는 그것만으로 설치 근거가 되지 않는다.

| 설계할 부분 | 적용할 스킬 |
| --- | --- |
| Unity 게임의 씬 구성, 플레이 규칙, 씬 교체 때 판 상태를 보존하는 주체 | `unity-game-architecture` |
| Godot 게임의 노드·씬 조합, 신호 연결, 방을 바꿀 때 유지할 상태 | `godot-game-architecture` |
| Unreal 게임의 Pawn·Controller·PlayerState 수명, 부활이나 맵 이동, 서버의 판정 권한 | `unreal-game-architecture` |
| Flutter 앱에서 화면 이탈 후에도 이어지는 작업, 화면 상태와 저장·동기화 책임 | `flutter-app-architecture` |
| Rust 프로그램에서 모듈과 crate 경계, 입출력 오류나 동시 쓰기를 책임지는 주체 | `rust-software-architecture` |

범용 설계로 충분하면 바로 진행한다. 여러 기술이 실제로 하나의 사용자 흐름을 맡으면 각각 필요한 항목을 선택한다. 목록 밖의 기술은 현재 환경에 제공된 관련 스킬과 프로젝트 근거를 활용한다.

## 선택한 스킬 가져오기

1. 이미 제공된 스킬이면 현재 환경이 선택한 정확한 진입 경로를 사용한다. 같은 이름의 다른 사본이 있어도 이 경로를 유지한다. 파일 기반 설치라면 같은 스킬 루트에 있는 `<이름>/SKILL.md`도 확인한다.
2. 선택한 스킬이 없으면 이 범용 스킬에 포함된 `scripts/ensure_specialist.py`를 Python 3으로 실행한다. 아래 명령의 스크립트 경로는 **이 스킬의 폴더 기준**이다. 게임이나 앱의 작업 폴더에서 부를 때는 스크립트의 실제 절대 경로를 사용한다. 필요한 이름별로 한 번씩 호출한다. 기본 저장 위치는 `$CODEX_HOME/skills` 또는 `~/.codex/skills`이다. 사용자가 별도 스킬 설치 위치를 지정했다면 `--dest <스킬 루트>`를 전달한다.

   ```text
   python3 scripts/ensure_specialist.py flutter-app-architecture
   ```

3. 기존 사본과 신규 설치 모두 실제로 열 `SKILL.md`를 오프라인으로 조회한다. 아래 마지막 인수에는 환경이 선택했거나 설치기가 출력한 절대 경로를 넣는다. 조회 후 같은 파일을 이번 요청에서 읽고 지침을 적용한다.

   ```sh
   python3 scripts/ensure_specialist.py flutter-app-architecture --status --json --entry "/path/to/flutter-app-architecture/SKILL.md"
   ```

4. 최종 응답에 **사용한 전문 스킬당 한 줄**을 남긴다. `verified_tag`가 있으면 그 태그와 ‘배포 파일 일치’를 적고, 카탈로그 권장과 다르면 둘 다 적는다. 추가 파일만 있을 때는 ‘로컬 파일 추가’를 붙인다. `modified`이면 설치 출처와 변경·누락 경로를, `ambiguous`면 후보 태그를 적는다. 선언만 있으면 ‘선언 버전 · 배포 내용 미확인’, 단서가 없으면 ‘버전 미확인’으로 쓴다. 판정의 경고도 관련된 경우 알린다. 수정본을 사용하기로 했다면 그 파일을 그대로 읽는다.

[배포 목록](specialists.json)은 권장 태그와 ZIP 해시를 담고, [배포 인덱스](release-index.json)는 과거판을 포함해 각 ZIP의 파일 바이트를 기록한다. `--status`는 로컬만 읽는다. 설치된 홈에서 확인하려면 `--entry` 대신 `--dest <스킬 루트>`를 쓸 수 있다. 조회 성공(종료 0)과 파일 일치 여부는 별개다.

Python 3이 없는 환경에서는 가능한 파일 도구로 실제 사본의 배포 파일 전체를 인덱스와 대조한 경우에만 일치를 표시한다. 버전 파일만 읽을 수 있으면 ‘선언’, 파일 API가 없으면 제공자가 공개한 버전·출처만 적고 ‘배포 내용 미확인’으로 표시한다. 신규 설치가 필요하고 네트워크와 해시 도구가 있으면 배포 목록의 `https://github.com/Ddrubok/<이름>/releases/download/<tag>/<이름>.zip`을 받아 ZIP의 SHA-256을 확인한 뒤 이름이 같은 폴더를 설치한다. 기존 폴더는 보존한다. 오프라인 요청 또는 권한 제한 시 가능한 로컬 설계를 진행하고 확인하지 못한 부분을 밝힌다. 해시가 다른 다운로드는 사용하지 않는다.

## 두 기술을 연결하는 예

Flutter 앱의 A와 B가 Rust API에 같은 시간대를 예약한다. Flutter는 요청 ID를 재시도에 재사용한다. Rust 쪽은 같은 요청의 기존 결과를 찾고, 슬롯의 유일성 제약과 요청 결과를 같은 트랜잭션에서 확정한다. 아래는 A의 요청이 먼저 커밋된 경우다.

| 확인 시점 | A 화면 | B 화면 | DB 예약 수 |
| --- | --- | --- | --- |
| A가 전송 후 응답 전에 화면을 닫음. B가 같은 슬롯을 신청함 | 화면 닫힘, 요청 ID 보존 | 이미 예약된 시간 | 1 |
| A가 돌아와 같은 요청 ID로 재시도 | 처음 확정한 예약 번호와 성공 표시 | 충돌 결과 유지 | 1 |

실제 출력에는 조회한 Flutter와 Rust 사본의 버전 판정을 각각 한 줄로 붙인다. 화면 색만 바꾸는 요청은 기존 UI에서 처리할 수 있다.
